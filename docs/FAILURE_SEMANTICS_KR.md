# 도착할 수 없는 지도의 결과값

2026-10-29. 학생이 현재 연구 질문을 정리하는 과정에서 다음 질문을 제시했다.

> 종착지까지 무슨 짓을 해도 갈 수 없을 때 결과값이 어떻게 나오는지 궁금해

이전 실험 이후 학생이 제시한 질문이다. 최초 실험 전 가설이나 결과 예상으로 소급하지 않는다. 아래 지도·예산·기대 API 동작과 실행·검증은 AI 지원이다.

## 고정 예제

```text
S..
..#
.#G
```

벽과 이동 규칙을 고정하고 상하좌우로만 움직인다. G 위와 왼쪽은 벽이고 오른쪽·아래는 지도 밖이다. 벽을 제거하거나 대각선 이동을 허용하는 다른 문제와 구분한다.

[입력](../experiments/unreachable-goal.scenario.json)과 AI의 기대 동작을 `d52a8ac2242c510d015e77b203b6a195d014dc53`에 커밋한 뒤 기존 도구로 실행했다. 충분한 예산 300과 작은 예산 2는 결과를 보기 전에 정했다. 학생은 별도의 결과 예상을 제시하지 않았다.

## 실제 반환값

충분한 예산에서는 A* FIFO·Greedy·Dijkstra 모두 다음 값을 반환했다.

```json
{
  "success": false,
  "reason": "UNREACHABLE",
  "path": [],
  "pathLength": null,
  "expanded": 6
}
```

`null`은 반환된 이동 경로가 없다는 뜻이다. 0번 이동으로 성공했다는 뜻이 아니다. 이 예제는 시작점과 연결된 6칸을 검토한 뒤 후보가 소진되어 종료했다.

| 같은 지도에서의 조건 | 실제 reason | 검토 칸 수 | 그 결과로 알 수 있는 범위 |
|---|---|---:|---|
| 예산 2 | BUDGET_EXCEEDED | 2 | 제한 전에 경로를 찾지 못함; 이 상태값만으로 경로 부재를 확정하지 않음 |
| 예산 300 | UNREACHABLE | 6 | 탐색을 소진했고 고정된 지도·이동 규칙에서 목표에 도달할 경로가 없음 |
| 무제한 참고 실행 | UNREACHABLE | 6 | 같은 도달 불가 결과 확인 |

두 경우 모두 success=false이고 path=[]·pathLength=null이므로 실패 이유를 함께 읽어야 한다. 예산이 먼저 끝난 결과만으로 도착 불가라고 단정하지 않는다. 표의 세 알고리즘은 이 예제에서 같은 값을 냈으며, 모든 지도에서 검토 순서나 수치가 같다는 주장은 아니다.

## 검증과 범위

[원시 결과](../data/failure-semantics/unreachable-goal-run-01.json)와 [검증 기록](../data/failure-semantics/unreachable-goal-validation-01.json)에 세 알고리즘의 무제한 결과와 예산별 결과 6개, 입력·소스·산출물 해시, 역할과 한계를 보존했다. 별도의 격자 문자 기반 flood-fill로 S에서 도달 가능한 칸이 6개이고 G가 포함되지 않음을 확인했다. 이 검증은 planner나 makeMap을 호출하지 않았다.

코어·실행 도구는 기존 23개 테스트의 소스와 동일하다. 입력만 추가했으므로 전체 테스트를 반복하지 않고 새 도달성·반환 필드·예산별 결과를 직접 검증했다. 실제 실행은 AI가 했으며 학생이 직접 코드를 작성하거나 실행한 것으로 표시하지 않는다. 관련 없는 연습 파일 변경은 건드리지 않았고 작업공간 상태를 기록했다.

현재 브라우저의 **지도 30장 비교는 도착 가능한 지도만 채택**하므로 이 예제는 별도의 실패 의미 확인이다. 도착 불가 사례를 그 묶음의 분모에 나중에 섞지 않는다. 실제 로봇의 센서·이동 실패를 측정한 결과도 아니다.

## 학생의 해석과 반환값 구분

두 실패를 구분하는 이유를 묻자 학생은 다음과 같이 답했다.

> 도착 불가는 예산 초과가 없더라도 절대 값이 나올 수 없어.

원문을 보존하고 AI의 보충 설명은 별도로 둔다. 고정된 지도에서 경로가 없다면 예산 제한을 없애도 성공 경로는 나오지 않는다. 그러나 프로그램의 반환값 자체가 없는 것은 아니다. `success=false`와 `reason=UNREACHABLE`이라는 실패 객체를 반환한다. 학생의 ‘값’이라는 표현을 성공 경로와 반환 객체의 구분을 이미 완전히 설명한 것으로 확대하지 않는다.

## 후속 비교 — 길은 있지만 예산이 작은 경우

AI가 G 왼쪽 (1,2)의 벽만 열어 다음 대조 지도를 제안했다. 위쪽 벽은 그대로다.

```text
S..
..#
..G
```

[연결 지도 입력](../experiments/reachable-goal-budget-control.scenario.json)은 동일한 출발·목표·다른 벽·예산 2/300을 유지한다. A* ①에서 예산 2일 때 어떤 상태가 반환될지 묻자 학생은 **예산 초과**라고 답했다. API 설명 이후의 안내된 실행 전 예상이며, 다른 알고리즘·예산·이동 횟수의 예상으로 확대하지 않는다. 예상과 ready 입력을 `93491c1ef104df472356278820c2a937600388f5`에 커밋한 뒤 AI가 실행했다.

## 연결 여부와 예산을 함께 비교한 결과

| A* ① | 예산 2 | 예산 300 |
|---|---|---|
| 원래 도착 불가 지도 | BUDGET_EXCEEDED, 2칸 검토 | UNREACHABLE, 6칸 검토 |
| 벽 하나 연 연결 지도 | BUDGET_EXCEEDED, 2칸 검토 | 성공, 4번 이동·8칸 검토 |

학생이 제시한 예산-2 상태 예상은 결과와 일치했다. 연결 지도는 예산 300과 무제한 참고 실행 모두에서 실제 경로를 찾았다. 같은 조건의 Greedy·Dijkstra도 예산 2에서는 예산 초과, 300에서는 4번 이동 경로를 반환했다. 단, 검토 칸 수는 Greedy 6, Dijkstra 8로 다르다.

다음은 **AI의 분석**이다. 두 지도 모두 예산 2의 반환 상태가 같지만 충분한 예산에서는 도착 불가와 성공으로 구분된다. 따라서 작은 예산의 초과 결과만으로 경로가 없다고 결론 내릴 수 없다. 실패할 때도 반환 객체는 존재하며, 경로가 없을 때 null인 이동 횟수를 0으로 바꾸어 읽지 않는다.

[연결 지도 원시 결과](../data/failure-semantics/reachable-goal-budget-control-run-01.json)와 [전후 검증 기록](../data/failure-semantics/reachable-goal-budget-control-validation-01.json)에 단일 (1,2) 변경, 고정 조건·소스, 원시 상태·경로와 역할을 보존했다. 별도 격자 BFS가 목표 연결과 최단거리 4를 확인했고 성공 경로도 검증했다. 코어·실행 도구는 기존 23개 테스트의 소스와 같아 전체 테스트를 반복하지 않고 입력·경로·반환 필드를 직접 확인했다. 검증 재실행을 새 독립 지도 표본으로 세지 않는다.

## 학생의 대조 실험 해석과 코드 연습

결과를 본 뒤 예산 초과만으로 길이 없다고 단정하면 안 되는 이유를 물었고 학생은 다음과 같이 답했다.

> 길이 있는데도 검토 예산을 줄이면 예산 초과가 떠 버리니까 그것만 보고 길이 없다고 단정하면 안되지

이는 안내 후 실제 연결 지도의 실패/성공 대비를 근거로 한 해석이다. 독립적인 구현이나 API 설계로 확대하지 않는다. 원래의 질문, 실행 전 상태 예상, 실행 후 해석은 시점을 구분해 보존한다.

다음은 [실패 이유 분류 연습](../practice/03-failure-reason.mjs)이다. AI가 기존 원시 결과 4개를 읽는 미완성 틀을 제공했고, 학생은 실패 이유가 담긴 결과 필드를 선택해 한 군데를 직접 수정할 예정이다. 아직 저장·수정·실행이 확인되지는 않았다. 이 연습은 새 경로 탐색 실험이나 학생의 독립적인 전체 분류기 구현이 아니다.

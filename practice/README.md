# 입력 수정과 결과 해석 연습

`01-path-change.mjs`는 AI가 제공한 산술 연습 예제다. 실제 경로 탐색이나 새 연구 결과가 아니라, 코드에서 실험 입력을 직접 바꾸는 연습이다.

1. `const after = 4;`를 `const after = 10;`으로 바꾸고 저장한다. `before = 8`은 유지한다.
2. 실행하기 전에 결과 숫자와 이동 거리가 늘었는지 줄었는지를 예상해 적는다.
3. 저장했다고 알려 주면 변경한 줄을 함께 확인하고 실행한다. 실행 명령은 `node practice/01-path-change.mjs`다.

파일 제공과 예제 구현은 AI 지원이다. 학생이 실제 저장한 변경, 실행 전 예측, 실행 주체는 확인한 뒤 별도로 기록한다. 이 산술 예제 자체는 경로 탐색 알고리즘 개선이 아니다.

첫 저장 시도: 사용자는 `저장했어/2`라고 답했지만, 파일은 `before = 10`, `after = -8`이었다. AI가 이 상태를 별도 커밋으로 보존한 뒤 실행한 결과는 -18이다. 이후 사용자가 안내에 따라 `before = 8`, `after = 10`으로 수정·저장한 것이 확인됐고, AI가 재실행한 결과는 2였다. 계산 방법과 정답을 설명한 뒤의 안내된 수정이므로 새로운 독립 예측으로 취급하지 않는다. 두 시도의 입력·출력·실행 주체는 `01-attempt-log.md`와 `data/learning/practice-01-attempt-0*.json`에 각각 보존했다.

## 두 번째 파일 — 실제 길찾기의 검토 예산

`02-planning-budget.mjs`는 기존 `src/core.mjs`의 A*와 Greedy를 같은 지도에서 실행하는 AI 제공 도구다.

```text
S . .
. # .
. . G
```

`budget`은 이동 횟수가 아니라 검토할 수 있는 칸 수다. 이 구현은 출발점과 도착점도 센다. 지도·알고리즘 코드는 유지하고 예산만 변경한다.

1. `const budget = 8;`을 `const budget = 5;`로 바꾸고 저장한다.
2. 실행 전에 두 방법 모두 길을 찾을지, 한 방법만 찾을지 예상해 적는다. 이전 안내에서 이 지도의 결과를 이미 봤으므로 이것은 기초 확인 연습이며 새로운 독립 예측 실험으로 주장하지 않는다.
3. 저장했다고 알려 주면 실제 변경을 확인·커밋한 뒤 `node practice/02-planning-budget.mjs`로 실행한다.

파일 제공과 예산 8의 초기 동작 확인은 AI 작업이다. 이후 사용자의 저장 보고와 예산 8→5 한 줄 수정이 확인됐다. 입력을 먼저 커밋한 뒤 AI가 실행한 결과, A*는 5칸을 검토하고 예산 초과로 멈췄고 Greedy는 5칸을 검토해 4번 이동하는 경로를 찾았다. 실행 기록은 `02-budget-log.md`와 `data/learning/practice-02-budget-5.*`에 보존했다. 학생의 사후 설명은 아직 받지 않았다. 이 연습은 탐색 알고리즘의 구현 변경이나 일반 성능 비교가 아니다.

2026-10-28에는 사용자가 예산을 5→8로 다시 수정하고, 실행 전에 `성공하지 않을까`라고 예상했다. AI가 실행한 결과 두 방법 모두 4번 이동 경로를 찾았고, 검토한 칸 수는 A*=8, Greedy=5였다. 원시 결과는 `data/learning/practice-02-budget-8.*`에 보존했다. 같은 지도에서 예산만 늘렸을 때의 동작을 확인하는 안내된 학습이며, 앞서 설명한 결과와 독립된 새 연구 예측은 아니다.

## 세 번째 파일 — 실제 결과의 실패 이유 분류

[03-failure-reason.mjs](03-failure-reason.mjs)는 AI가 제공한 미완성 틀에서 시작한 필드 선택 연습이다. 기존 두 지도의 A* 결과 4개를 읽으며 코어 탐색을 새로 실행하거나 원시 데이터를 수정하지 않는다. 실제 앱의 분류 버그를 고치는 작업이나 학생이 전체 분류기를 구현했다는 증거가 아니다.

처음 학생에게 제시한 수정 자리는 한 군데였다.

```js
const fieldName = '____';
```

`success`는 성공 여부, `reason`은 실패 이유를 담는 결과 필드다. 실패 이유를 구분하려면 어떤 필드를 읽어야 할지 선택해 `____`에 필드 이름을 넣고 저장한다. 따옴표와 다른 코드는 유지한다. `result[fieldName]`은 그 이름의 필드 값을 읽는 문법이다.

2026-10-29 사용자가 저장을 보고했고, 실제 파일에서 `____`→`reason` 한 곳만 바뀐 것을 확인했다. 안내된 한 필드 선택·저장으로 구분해 `3bd0cf1828c0f4855a7a58e378b94086bcae8863`에 먼저 커밋했다. 이후 AI가 `node practice/03-failure-reason.mjs`로 실행해 예산 초과 두 사례, 도착 불가 한 사례, 성공 한 사례가 구분되는 것을 확인했다. 빈칸 상태의 ‘아직 분류하지 않음’은 남지 않았다.

[실행·검증 기록](../data/learning/practice-03-run-01.json)과 [표준 출력](../data/learning/practice-03-run-01.stdout.txt)에 원시 데이터 해시·입력 커밋·역할을 보존했다. 학생의 실제 한 곳 변경만 안내된 기여이며 AI가 제공한 함수·분기·데이터 읽기 코드는 학생 작업으로 귀속하지 않는다. 실제 실행과 검증도 AI 작업이고, 새 지도 표본이나 알고리즘 개선 실험이 아니다.

필드 선택 이유를 묻자 학생은 **그게 예산 초과 때문인지 아니면 진짜 길이 없는 건지 알아야지**라고 설명했다. 이는 결과 확인 후 안내된 이유 설명으로 기록한다. 다음은 이 과제에서 직접 한 일과 AI 지원을 구분하는 기여 진술 두 문장을 작성하는 단계다.

[실행 확인](../data/learning/endpoint-feedback-validation-01.json)은 저장된 성공 입력6,1의 출력이 이전과 같고, 메모리 안에서만 바꾼 실패 입력8,4는 이전 출력에 안내문만 추가됨을 보존한다. 같은 지도/몸체/예산200이며 알고리즘·숫자 표는 바꾸지 않았다. 다음은 학생이 goal을8,4로 바꿔 저장하고 같은 명령을 실행해 새 안내문을 확인하는 단계다.

메모장 편집 안내 후 학생이 완료를 보고했고, 실제 goal6,1→8,4 한 줄 수정만 확인했다. [수정 기록](../data/learning/endpoint-feedback-guided-edit-01.json)에 보존했으며 새 실행이나 안내문 관찰은 아직 보고 전이다. 다음은 PowerShell에서 같은 명령을 다시 실행하고 표 아래 한국어 안내문을 공유하는 단계다.

학생이8,4의 실패 표를 공유한 뒤, 한국어 안내문도 표시된다고 명시적으로 확인했다. [사용자 확인 기록](../data/learning/endpoint-feedback-student-report-01.json)은 두 채팅 보고를 보존하고 독립 실행 관찰과 구분한다. 문구와 조건문은 AI 작성이다. 마지막 확인은 메모장에서 goal을6,1로 되돌려 저장하고 같은 명령을 실행한 뒤, 정상 결과에서 이 경고가 나오지 않는지 공유하는 것이다. 정상 사례의 사용자 확인은 아직 보고 전이다.

정상 사례에서도 학생이6,1의 도착 성공/길이8/검토31 표를 공유했고 경고가 “안 나옴”이라고 명시했다. [정상 사례 보고](../data/learning/endpoint-feedback-student-report-02.json)는 실제 한 줄 복원과 사용자의 출력·부재 확인을 기록하며 독립 실행 관찰과 구분한다. 안내문 기능의 두 알려진 사례 확인은 이 단계에서 마무리한다. 다음은 [설명용 두 이동 순서의 방향 전환 횟수 세기](../experiments/path-turn-count-01.design.json)이며 실제 주행·회전 시간이나 에너지 실험은 아니다.

## 경로 모양 지표 — 방향 전환

학생은 설명용 A/B 순서의 방향 전환을 **1번/5번**으로 셌다. [원문](../data/learning/path-turn-count-answer-01.json)과 AI 지원 범위를 구분한다. AI가 `directionChanges` 열을 추가해 성공 경로의 방향 전환을 자동 계산한다. 실패는 `null`이며 출발 방향 맞추기는 세지 않는다. [방법·실행 근거](../docs/PATH_DIRECTION_METRIC_KR.md)는 같은 지도/몸체/예산200에서6,1의 길이8·검토31·방향 전환6, 실패8,4의null을 확인한다. 새 지표 검사5개와 반환 벡터 재계산은 통과했으며 기존 전체 검사는 반복하지 않았다. 다음은 오른쪽3칸·아래3칸·총6칸 이동하면서 방향을 정확히2번 바꾸는 순서를 학생이 직접 만드는 설명용 과제다. 아직 순서는 받지 않았다.

학생이 `↓→→→↓↓`를 제시했다. [원문](../data/learning/path-turn-design-answer-01.json)을 먼저 보존한 뒤 [같은 지표와 직접 계산](../data/learning/path-turn-design-validation-01.json)으로6칸·오른쪽3/아래3·도착3,3·전환2회를 확인했다. 학생이 만든 설명용 순서이며 현재 지도·몸체의 실제 통과 실험은 아니다. 다음은 이동1점/방향 전환2점이라는 AI 제시 가상 규칙에서 두 경로 점수를 비교하는 과제다.

## 다섯 번째 파일 — 방향 전환 가상 점수

[05-path-score.mjs](05-path-score.mjs)는 고정된 설명용 X/Y 경로에 `세계 길이 × 1 + 방향 전환 횟수 × perDirectionChange`를 적용하는 AI 제공 도구다. 학생은 먼저 **X: 16점, Y: 12점 -> Y**라고 계산·선택했다. [원문](../data/learning/path-turn-cost-answer-01.json)과 [AI 실행·검사](../data/learning/path-turn-score-run-01.json)를 구분한다. 초기 `perDirectionChange = 2`에서X16/Y12가 확인됐다.

세계 길이를 쓰므로 반 칸으로 나눈 구간 수를 이동 거리로 오인하지 않는다. 점수는 임의 단위이며 초·에너지나 실제 로봇 보정값이 아니다. 자동 길찾기 규칙도 바꾸지 않는다. 점수 검사5개와 기존 방향 검사5개, 총10개가 통과했고 이전101개 전체 검사는 반복하지 않았다. 다음은 전환 계수만0.5로 낮춘 경우의 X/Y 점수와 선택을 먼저 계산하는 [과제](../experiments/path-turn-cost-sensitivity-01.design.json)다. 해당 조건을 아직 실행하지 않았다. 학생 답을 받은 뒤에만 파일의 `perDirectionChange`를2→0.5로 바꿔 저장·실행하는 단계로 진행한다.

학생은 전환 계수0.5에서 **X: 8.5, Y: 9, X**라고 답했다. [원문·계산과 실행의 구분](../data/learning/path-turn-cost-sensitivity-answer-01.json)을 보존한다. 확인 당시 파일은 여전히 `const perDirectionChange = 2;`였으므로 다음은 메모장에서 이 한 줄만 `const perDirectionChange = 0.5;`로 바꾸고 저장하는 단계다. 실제 차이·실행 주체·출력은 이후 확인하며 기존2점 결과는 유지한다.

사용자가 저장을 보고했고 실제로 `perDirectionChange = 2`→`0.5` 한 줄만 달라진 것을 확인했다. [입력 기록](../data/learning/path-turn-score-edit-01.json)과 소스 `6437536b438b76aab4243032c5ef56b7c95f4d2d`를 먼저 보존한 뒤 AI가 실행했다. [새 결과·짝 비교](../data/learning/path-turn-score-run-02.json)는 X8.5/Y9와 X선택을 확인하며, 기존2점의 X16/Y12·Y선택 결과는 덮어쓰지 않았다. 새 알고리즘이나 경로가 아니라 가정한 점수 계수의 민감도 확인이다. 학생의 계산·수정과 AI 실행을 구분한다. 다음은 두 경로가 그대로인데 선택이 바뀐 이유를 학생이 한 문장으로 설명하는 단계다.

학생의 사후 설명은 **방향 전환을 그리 중요하게 보지 않았어**였다. [원문과 맥락](../data/learning/path-turn-cost-interpretation-01.json)은 낮아진 전환 계수의 영향에 대한 안내된 해석으로 기록한다. 다음 [각도 과제](../experiments/heading-angle-01.design.json)는 처음 오른쪽을 보는 상태에서 아래 또는 왼쪽을 보려면 최소 몇 도 돌아야 하는지 묻는다. 기존 변경 횟수 지표의 출발 정렬 제외 규칙은 그대로이며, 이 별도 설명에서 출발 방향을 명시적으로 도입한다.

## 여섯 번째 파일 — 처음 방향과 회전 각도

학생의 **A: 90도 / B: 180도** [답](../data/learning/heading-angle-answer-01.json)을 먼저 보존한 뒤 AI가 [06-path-rotation.mjs](06-path-rotation.mjs)와 회전 지표·검사를 만들었다. `initialHeading = 'right'`에서 같은 설명용 X/Y 경로의 처음 정렬과 경로 중 각도를 구분한다. [결과와 근거](../docs/PATH_ROTATION_KR.md)는X0+450=450도, Y90+180=270도를 확인한다. 새 검사6개와 기존 방향 검사5개, 총11개가 통과했다. 기존101개 전체 검사는 반복하지 않았다. 학생 답과 AI 구현·실행을 구분하며 실제 로봇의 주행·시간 측정은 아니다. 다음은 처음 방향이아래일 때 X첫이동오른쪽/Y첫이동아래에 맞추려면 출발 전에 각각 몇 도 필요한지 답하는 과제다. 학생은 [X90도/Y0도](../data/learning/path-rotation-initial-heading-answer-01.json)로 첫 이동 전 정렬 각도를 답했다. 확인 당시 파일 값은 `right`였으므로 다음은 메모장에서06파일을 열고 `const initialHeading = 'right';` 한 줄을 `const initialHeading = 'down';`으로 바꾸어 저장하는 단계다. 아래 방향 구성 실행이나 실제 수정은 아직 확인하지 않았다.
